# Verified behaviour

Facts tested live, dated, so a reader can tell what may have changed since.

## 2026-10-30

- **Cursor windows on KDE Plasma 6.8.1 / Wayland** (Claude Code extension 2.1.312): all 5 open Cursor windows belonged to one process (`VSCODE_PID`), so a pid can't pick a window. Captions read `<tab> - <workspace folder> - Cursor`. The extension's `claude` process starts with `CURSOR_WORKSPACE_LABEL=<workspace folder>` and `CLAUDE_CODE_ENTRYPOINT=claude-vscode` (`/proc/<pid>/environ`); hooks are its children.
- **A KWin script can flag one window on Wayland.** Loaded with `qdbus6 org.kde.KWin /Scripting org.kde.kwin.Scripting.loadScript FILE NAME` and started with `qdbus6 org.kde.KWin /Scripting/Script<id> org.kde.kwin.Script.run`, a script listed the windows (`print()` lands in the user journal) and set `demandsAttention = true` on one inactive Cursor window; a second script read it back as true, a third cleared it. The panel's visible flash was not checked. `kdotool` and `xdotool` are not installed.
- **`hooks/attention.py` runs from the extension's shell** (it inherits `CURSOR_WORKSPACE_LABEL` and `CLAUDE_CODE_ENTRYPOINT=claude-vscode`): a Stop payload exited 0 with empty stdout in 0.05 s and left no temp script, and `flash()` returned true (`loadScript`, `run` and `unloadScript` all succeeded) in 16 ms. This window was active, so nothing was flagged. A later picker offering `/clear` flashed this window's panel entry (the user was in another window) and popped up the handoff notification. This session had started before `./install.sh --attention` added the hooks, so a running extension session picks up new hooks without a restart.
- **Stop hooks fire inside the Cursor extension:** 93 `stop_hook_summary` transcript entries (the Codex plugin's Stop hook) in 36 of the 40 most recent transcripts, all `entrypoint: claude-vscode`. Notification hooks: untested, no installed hook listens for them.
- **Background tasks in a transcript:** a background Bash call's `tool_result` says `Command running in background with ID: <id>`; its end appears as `attachment` and `queue-operation` lines holding `<task-id><id></task-id>`. Later assistant lines can quote the same tag.
- **The extension can open a conversation with a prompt typed in, but never sends it** (extension 2.1.312's `package.json` and bundle, read, not clicked). `claude-vscode.newConversation` takes no arguments; `claude-vscode.editor.open(sessionId, initialPrompt, …)` and the URI handler `cursor://anthropic.claude-code/open?prompt=…` (which calls `primaryEditor.open`) open a new tab, and the webview only puts `initialPrompt` into the input box (`setInputText`). No command sends prompt text or clears the current session. The terminal CLI's `showClearContextOnPlanAccept` setting adds "Yes, clear context …" to plan approval; the webview's own plan dialog has no such option.
- **`/clear` → `/next` costs about 3 s per handoff** (all local transcripts, 2026-10-14 to 10-30). Of 318 sessions started by `/clear`, 261 began with a bare `/next`, a median of 2.7 s later (p75 3.2 s); 56 with `/next` plus instructions; 1 with other short text; none with longer free text. Before 10-14 (`/next` was added 10-13), 42 of 44 free-text first prompts were hand-written handoff continuations.
- **Codex's `workspace-write` sandbox blocks writes through a `--link` symlink** (codex-cli 0.159.1, `codex sandbox -c 'sandbox_mode="workspace-write"'`, workspace and link target both under `~/.cache`, outside the writable `/tmp`). `echo x > link/f` failed with `Read-only file system`, as did a direct write to the target folder; a write to `own.txt` in the workspace succeeded, and `ls link/` read through the link. A field run (2026-10-30) whose brief asked for output under a linked folder wrote it to `/tmp` instead; its `--verify`, outside the sandbox, wrote the intended path. Not tested under Cursor's sandbox.
- **Session-mode allocation in period 2** (session log, first start rows from 2026-10-26 17:20:51 to 10-30 04:30 UTC, ghosts included): the 214 drawn sessions came out 141 / 48 / 25 (orchestrator / claude-only / vanilla) against 149.8 / 32.1 / 32.1 expected under 70/15/15, χ² 9.96 (2 df, p ≈ 0.007). Replaying `draw_mode` on each row's stored `u` and weights gives the logged mode for all 214. 48 `u` values fall in [0.70, 0.85), where 32 are expected; all 214 are distinct, and KS against uniform gives D 0.058 (critical value 0.093). 12 rows store the orchestrator weight as 0.6999999999999998, so a filter on exactly 0.7 drops them.
- **The start-row context hash stays fixed while the spare line changes** (the first live start rows with the new fields): the injected spare-pool line carries the reading's age and live percentages, so it differs between sessions. Two orchestrator start rows 7 minutes apart logged different spare lines and the same `context_sha256`, which `context_pin` reproduced from the unchanged rules 9 minutes after the first.

- **`git apply --3way` vs a dirty main tree, and a temp-index fix** (scratch repo, git 2.56.0). Snapshot S of a dirty main tree, worktree branch at S, delegate edits line 6, patch = `git diff --binary S` (only the delegate's line). Main tree then edits line 5 (adjacent). `git apply` fails (context); `git apply --3way` fails with `f.txt: does not match index`. Copy of the index + `git add` of the touched path in a temp index + `GIT_INDEX_FILE=tmp git apply --3way` prints `Applied patch to 'f.txt' with conflicts.`, `U f.txt`, writes `<<<<<<< ours` / `>>>>>>> theirs` markers into the working file, and leaves the real index untouched (`git status --short` shows ` M f.txt`). In a clean main tree, `git apply --3way` of a clean patch prints `Applied patch to 'g.txt' cleanly.` and stages the file (`M  g.txt`). `delegate apply --3way` now always uses the temp-index path so a clean 3-way stays unstaged.
- **`git apply --numstat` is cwd-relative** (this run's `changes.patch`, git 2.56.0). From the repo root it listed 6 paths; from `tests/` only `tests/test_include_uncommitted.py`. Paths outside the cwd are dropped, so a temp-index 3-way apply started in a subdirectory would omit root-level files and revive `does not match index`. `patch_paths` now passes `cwd=repo`.
- **`git apply --check --3way` conflict text is locale-dependent** (this machine, German translations installed). Under `LANGUAGE=de LANG=de_DE.UTF-8 LC_ALL=de_DE.UTF-8`, a conflicting `--check --3way` exits 0 and prints `Patch auf 'f' mit Konflikten angewendet.`; with `LC_ALL=C` it prints the English `Applied patch to 'f' with conflicts.` (still rc 0). Detection that keys on the English phrase therefore needs `LC_ALL=C` on the apply subprocess. `GIT_LITERAL_PATHSPECS=1` similarly stops a patch path like `tests/test_[a]sk.py` from matching `tests/test_ask.py` in `ls-files` / `add`.

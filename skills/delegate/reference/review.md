# Delegate review and completion

Read before steps 4 to 9 to review, fix, merge and clean up; paths such as `templates/` and `scripts/catalog.json` are relative to the skill folder.

4. **Cross-review** (non-trivial changes): `delegate review NAME` in the background. Other vendor by default (`--agent` / `--focus` override). Reviewer gets the brief plus the diff at `wt/.delegate/review-N.patch`; any single-file diff over 200 KB is replaced there by its header and a note (`--patch-max-kb`; `changes.patch` stays complete). Returns Verdict, findings, spec compliance. The packet shows the finding counts and up to 5 findings, high first; the rest are in the run directory's `review-<n>/last-message.md`. `status` warns if a reviewer changed the worktree. The reviewer is asked to challenge the brief too, but compliance reviews can approve wrong briefs. Check domain criteria yourself or ask the user before launch. Put known issues into `--focus` as "already handled: …, ignore"; listed as things to check, they come back as findings. A Codex xhigh review costs ~15 points of codex-5h: start it after your own first pass with those findings listed that way. For heuristic code (parsers, scanners, warnings), give real-data frequencies and a stopping rule ("forms that never occur in real input are low"), to bound reviews of rare forms. Reviewers can't run notebooks; for prose that interprets outputs, put a text dump of the executed outputs under `wt/.delegate/` and name it in `--focus`. A small follow-up round that your own read and a real-data check cover needs no second review.
   - **Prose or fact reviews** (`review --working-tree`): put a numbered source dump in a gitignored folder and `--link` it, and list the known doubts in the brief for the reviewers to answer one by one.
5. **Your own review. Never trust a summary.** Risk-based:
   - **Data / semantic modules** (parsers, validation, matching, accounting, safety guards): read the core files whole; for the tests, a `grep -n "^def test"` outline plus 2–3 tests read in full (~25k tokens for one module).
   - **Rendered output** (notation, plots, UI): look at one real render before accepting an APPROVE, and give the reviewer the PNG; passing tests can miss visual errors.
   - **Moved or ported code:** run the same adversarial inputs on base and build and compare the outputs. A green verify or an APPROVE does not replace this pass: an APPROVE with no findings and a green verify each let regressions in moved code through (two field reports). Give each "departure" the delegate lists, and each risk line saying the brief allowed it, one targeted read or probe.
   - **UI, docs, plumbing:** review the packet's file list and Digest risks, then read only the flagged spots.
   - Send large documents to `delegate ask` instead of reading them here.
   - Re-run tests and the dry run yourself against real data. Adjudicate each reviewer finding; some are wrong.
   - Read the core while the cross-review runs. Independent checks can find gaps reviewers miss.
6. **Fix rounds.** Brief with accepted findings (or `--from-review N`), then `delegate followup NAME --brief fixes.md`. Archives to `round-<k>/`, resumes the same session and `--verify`. After ~3 rounds without convergence: `--fresh --model <stronger>`. When the last review leaves only 1–10 line fixes, make them inline with tests; another round plus a re-review cost about 0.6M Codex tokens for the same result. A fix brief states the invariant the fix restores and asks for a test of the neighbouring case; for a tokenizer or parser rule, list the adjacent syntax classes (shell: redirects with `&` including `2>&1`, continuations, quoting) with one test each, so a lone-`&` rule preserves redirects. Before a fix brief prescribes a helper or option, read its docstring for defaults and clipping, and let the delegate quote the value it prints to avoid misattribution. Pass your hand-probe script to `followup --verify` beside the gate. Before a round on findings against a warning-only heuristic, count real inputs with that form: zero hits make it a documented limit.
7. **Merge.** `delegate apply NAME --check`, then `delegate apply NAME` (uncommitted on the main tree). Commit only when the user asks, small local commits on a feature branch included. A merge listed in a handoff is not approval: check CI, ask in one line, keep working. In auto mode, collect the destructive or outward git steps (`git rm` of tracked data, commit, push, PR, merge, tag) into one explicit approval request at the end of the item; the classifier blocks them one at a time otherwise. `--3way` if the main tree moved (temp index: updates working files, stages nothing). After merging several delegates' work: one real integrated end-to-end pass with the same cache state as production (cold if production is cold), plus a preflight of offline inputs before long network phases.
8. **Clean up.** `delegate cleanup NAME` removes worktree and branch, keeps the run record; refuses while unapplied. `--purge` deletes the record; `--force` discards changes.
9. **Before outward-facing actions** (emails, scheduled crawls, publishing): check every quantitative claim in docs and briefs against the code that executes. For data releases, diff old and new output and check every changed headline value against a source, since passing gates can miss wrong labels. Changed cells outside the item's columns mean cache drift, not the change under review.

Delegates' summaries can be wrong when their code is right. Judge the patch and your own re-run.

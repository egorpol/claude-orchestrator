# Session rules

From the claude-orchestrator field reports (`feedback/`). They hold in every session, with or without delegation.

- **One work item per session.** At an item boundary above ~120k context, refresh the handoff (memory files plus `HANDOFF.md`: state, open PRs or runs, decided cases, next step), then offer "`/clear`, then `/next`" as a picker option before starting the next item, even after "go on" (a command can't run `/clear` itself): offered four times as a closing sentence, it was passed over while one session ran on to 223k. Below 120k, hand off too before a large item. New items: a finished build that turns into Q&A or a hand-paste loop, even on the same topic; a new topic; a "check everything" sweep above ~100k.
  - An item can stop before its last deliverable. When a handoff's next step bundles several deliverables, a prompt lists 4+ items, or each step adds ~10–15k, hand off at the first step boundary above ~120k and list the rest. When a step writes over ~40 KB, plan the handoff after code and tests. A handoff's next step names one deliverable that fits one session, and its internal boundary ("hand off once the gate is green, before docs").
  - Hand off before a wait of over an hour, and above ~100k refresh the handoff before a picker or hand-paste step the user may answer after a break: the turn after the wait rewrites the whole context at 2× (12.7% of logged orchestrator cost).
  - Close every item with a picker, never a prose line, offering "`/clear`, then `/next`" and, if the user writes field reports, `/field-report`.
- **`HANDOFF.md`** at the project root, where `/next` looks first; if the repo must not track it, list it in `.git/info/exclude` rather than moving it into a subfolder. State and next step first, under ~10 KB: cut a committed item to one line with its commit and the decisions that still bind. Commands run as written: full paths, every gate the next step needs with the interpreter or venv it runs in, a ready `--deselect` for known failures, and no scratchpad paths (give a path outside it or the command that rebuilds it). Always write it, even if it only points at a plan.
- **A commit, merge, push or tag in a handoff or plan is not approval**, and neither is a small local commit. Ask once at the end of the item, as a picker option bundling all git steps, and keep working meanwhile. Destructive git steps (`git rm -r`, reset, branch delete) wait for that picker too and run in their own Bash call.
- **Ask before accepting terms** or a licence on the user's behalf, even for a probe.
- **Decisions go in a picker** (`AskUserQuestion`) when the user chooses between 2–4 options: the recommended one first, labelled "(Recommended)", and in each description numbers measured in the same turn, on the worst real input for a data or file policy. A picker about local data includes plain "discard". No option may depend on typing into "Other"; use prose for open answers (a link, a name). Ask the question that decides the shape (audience, budget, GUI or CLI) before researching or writing for one shape.
- **Status lines:** before 2+ tool calls without text between them, one line saying what they are for; another at least every 3 calls, after an unexpected result, and before a call that may run over a minute. On a resume, the first line says which step, why it matters and what done means; restate it when the sub-goal changes.
- **Checks:** before a PR, check every changed headline value and every count or "all" claim against the source, measured in the same turn; passing gates are not enough, and public claims are checked against what is deployed. A hypothesis, a tool-behaviour claim and a fix that a reviewer or delegate suggests each get one cheap live probe first. Name the check that passed ("passes RNG"), not "validates", until the full gate has run. A probe that proves an absence ("no warnings") needs a positive control that does fire. Write changelog lines and claims before the final verification run, one check per claim. Never write an identifier (DOI, Wikidata QID, GND) from memory; look it up.
- **Shell:** the Bash tool runs zsh, not the user's fish. Don't `cd` away from the project root; use absolute paths, `git -C`, a tool's own directory flag or a subshell (7 of 26 reports did). Push in its own Bash call after the commit. Count before printing (`| wc -l`, then `head`).
- **Edits:** edit prose with a Python replace that asserts exactly one match, replacing the whole sentence when several changes fall in it; `sed` on wrapped Markdown silently matches nothing. Keep a structured file's formatting, and check the diff size before writing.
- **Reads:** read a file over ~1.5k lines through a grep outline and line ranges, and trim and downscale images to ≤1000 px wide before reading them.
- **Clean up only what this session created.**

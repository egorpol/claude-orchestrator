# Session rules

From the claude-orchestrator field reports (`feedback/`): work items and handoffs, decisions, data checks, shell and edits. They hold in every session, with or without delegation.

- **One work item per session.** At an item boundary above ~120k context, write or refresh the handoff (memory files plus `HANDOFF.md`: state, open PRs or runs, decided cases, next step). Then offer "`/clear`, then `/next`" in one line before starting the next item (`/next` continues from `HANDOFF.md`; a command can't run `/clear` itself), even after "go on". Below 120k, hand off too when the next item is large, such as docs that read or write tens of KB. Always write `HANDOFF.md`, even if it only points at a plan: a "continue from the handoff" that finds no file costs the next session several calls of transcript digging. These count as new items:
  - a finished build that turns into Q&A support or a hand-paste loop (the user posting prepared texts one by one), even on the same topic. Make "`/clear`, then `/next`" an option in the picker that closes the first answer: offered four times as a closing sentence, it was passed over while one session ran on to 223k;
  - the user turning to a different topic;
  - a "check everything" or sweep request above ~100k, above all one that reads images: one ran from 110k to 240k within a single prompt, with about 30 image reads. Trim (`magick -trim`) and downscale renders and crops to ≤1000 px wide before reading them.

  An item can stop before its last deliverable. When a handoff's next step bundles several deliverables, a prompt lists 4+ items, or a guided item grows ~10–15k per step, hand off at the first step boundary above ~120k and list the rest: five sessions (2026-10-14 to 10-17) each ended one item or one typed prompt at 241–328k. A handoff's next step names one deliverable that fits one session.

  Also hand off before a wait of over an hour. The prompt cache expires, and the first turn after the wait rewrites the whole context at 2×: 12.7% of all logged orchestrator cost, half of it from runs that finished after an hour. Above ~100k, refresh the handoff before a picker or hand-paste step that the user may answer after a break. Close every item with a picker, never a prose line, that offers "`/clear`, then `/next`" and, if the user writes field reports, `/field-report`: six sessions (2026-10-13 to 10-20) paid 10–18% of their cost units for one rebuild after a 61–281 min wait, three of them on `/field-report`.
- **`HANDOFF.md`:** at the project root, where `/next` looks first; if the repo must not track it, add `/HANDOFF.md` to `.git/info/exclude` rather than moving it into a subfolder. State and next step first, under ~10 KB. Two 29–31 KB handoffs, mostly done-item history, cost ~8k tokens per resume, so once an item is committed, cut its section to one line with the commit and the decisions that still bind. Write commands that run as written: full paths (`delegate` is on PATH only after `install.sh --bin`), known failing tests with a ready `--deselect` flag (a full `pytest -x` stopped at test 188 of 531 on one), and no paths into the session scratchpad (the next session gets a new one): give a path outside it or the command that rebuilds it.
- **A commit, merge, push or tag listed in a handoff or plan is not approval.** Neither is a small step: a local commit on a feature branch also waits. Ask once at the end of the item, as a picker option, bundling all git steps, and keep working on independent parts meanwhile. A destructive git step (`git rm -r`, reset, branch delete) waits for that picker too and runs in its own Bash call: bundled with other edits, the auto-mode classifier denied the whole call.
- **Terms on the user's behalf:** ask before submitting a form that accepts terms or a licence, even for a probe.
- **Decisions go in a picker.** When a reply asks the user to choose between 2–4 discrete options, ask with `AskUserQuestion`, not in prose. Put the recommended option first, labelled "(Recommended)", with measured numbers in each description. Use prose for open answers, such as a link or a name; no option may depend on typing into "Other", which came back as a bare selection. Ask an unstated quantity that shapes the plan (session length, audience, budget) before writing, not as an "assumption to confirm" afterwards: one outline revision took 15 edits.
- **Status lines:** before any run of 2+ tool calls without text between them (reads, probe chains, test/fix loops, Write and Edit sequences), write one line saying what they are for, and another at least every 3 calls. Write one also after an unexpected result, before the first diagnostic call, and right before a call that may run over a minute (installs, builds, notebook runs): all 9 harness status requests in three sessions (2026-10-13/14) came at those points. On a resume, the first line gives the plan position in plain words (which step, why it matters, what done means); restate it when the sub-goal changes.
- **Data changes:** before a PR, check every changed headline value against a source, and every count or "all" claim in public text against the data measured in the same turn; passing gates are not enough. Test a hypothesis with one cheap live sample before writing it into a plan. The same goes for a tool-behaviour claim in a doc or handoff ("the renderer draws X"): probe it on the current file, and keep the minimal example next to any such claim you write.
  - Name the check that passed ("passes RNG"), not "validates", until the project's full gate has run. Look for an existing validator in the project and its libraries before writing one. Before writing a script that drives a fixture, read the fixture's own check script for paths and setup.
  - Check an example meant for others in the tool they will use: the maintainers' online editor and schema version, a fresh venv with only the shipped install steps, a real JupyterLab (nbclient emulates widgets). A post checked only against the project's own schema cost ~16 calls and a round trip.
  - A change to scoring, ranking or keyword weights gets a before/after run on real inputs the same day: 53 unit tests passed while 6 off-topic posts jumped to the top tier. Check a UI fix at every variant its inputs depend on (widths, themes): a CSP hash of an injected style held only at 1280 px.
  - Headless browser checks: disable the cache, scroll the target into view, fail on console errors, and assert one rendered property (a dark-pixel share, a screenshot) beside the DOM state: a blank scan passed every DOM check.
  - A before/after diff of renders or exports first normalises generated IDs and random tokens; prove the normaliser on one identical-input pair. Verovio puts a random token into every SVG, so a raw diff always "differs".
  - When a note qualifies a headline value (a source's real date, say), carry it into every doc that states the value.
  - Doc examples with invented content use fictional IDs, never a real record's.
  - Never write an identifier (GND, VIAF, ISNI, Wikidata QID, DOI) from memory; look it up. Don't offer one, or a name or publisher, from memory for the user to confirm either: a from-memory publisher got a "yes", and only a later search kept it out of the file. Dates and names inherited from an import or a conversion are claims to check too.
  - Check public claims against what is deployed, not the checkout. Tally categorical values by exact match: a substring test (`'eu' in flag`) counted 252 where the source said 65.
- **Vague reports:** when the first check shows nothing wrong, show it and ask what is missing before widening the test matrix. Ten calls across browsers, widths and themes once failed to reproduce a complaint that was about taste.
- **Reads:** read a file over ~1.5k lines through a grep outline and line ranges, or hand the full read to a subagent that returns findings: one 2.8k-line read carried ~40k tokens through 70 later calls, ~14% of that session's cache reads.
- **Shell:** the Bash tool runs zsh, not the user's fish.
  - Push in its own Bash call after the commit: the secret guard scans only commits that exist when the call starts.
  - fish's `(cmd)` substitution fails; use `$(cmd)`.
  - An unquoted `$var` does not split into words; loop over a file list with `while read`.
  - Write scratch scripts to files rather than nesting heredocs.
  - Don't `cd` away from the project root. The new directory sticks, and later relative paths, `git add` and tools' config lookups run there: 5 of 15 sessions (2026-10-13 to 10-20) did it, and one strict build failed ~50 calls later. Use absolute paths, `git -C`, a tool's own directory flag, or a subshell `(cd sub && make)`, which leaves the shell where it was.
  - `=word` at the start of a word expands to a command path, so `echo ===` fails; use `echo ---`.
  - Quote globs and URLs meant for the called program (`--include='*.py'`, `'https://…?q=1'`); a glob that matches nothing aborts the command.
  - `pkill -f PATTERN` and `pgrep -f PATTERN | kill` can match their own shell's command line and kill it; stop a server with `fuser -k PORT/tcp` or a saved PID. With `run_in_background`, run the server in that command's foreground (no trailing `&`), so the task ends when the server does.
  - Run each long command as its own background task. Killing the child of an `a && b` chain lets the chain go on to `b`. Join independent probes with `;`: in an `&&` chain, a grep with no match silently skips the rest.
  - Count before printing: `| wc -l` or `uniq -c` first, then `head`; one log grep printed over 64 MB. Print one PASS/FAIL line per case plus the first error, and grep for those rather than `tail -N`, which cut results and kept whole tracebacks (~3k tokens per failed run). A probe of a library that may crash runs one subprocess per case and prints its return code; `$?` after a pipe is the last command's.
  - Keep stderr (no `2>/dev/null`) when a check is about warnings or logs; hidden renderer warnings took 4 calls to reproduce.
- **Edits:** edit prose with a Python replace that asserts exactly one match; `sed` on wrapped Markdown silently matches nothing. For several changes in one sentence, replace the whole sentence: overlapping pairs each match once and still eat text. A script that rewrites a structured file (JSON, a notebook, hand-formatted config) keeps the file's formatting: edit at text level or match its `indent`, and check the diff size before writing (a re-serialised notebook turned a 199-line diff into 1,477). For before/after checks, use `git show HEAD:path > tmp`, not `git stash`, which unstaged `git mv` renames.
- **Clean up only what this session created.**

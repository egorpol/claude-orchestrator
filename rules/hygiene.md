# Session rules

From the claude-orchestrator field reports (`feedback/`). They hold in every session, with or without delegation.

- **One work item per session.** At an item boundary above ~120k context, refresh the handoff (memory files plus `HANDOFF.md`: state, open PRs or runs, decided cases, next step), then offer "`/clear`, then `/next`" as a picker option before starting the next item, even after "go on" (a command can't run `/clear` itself). Take the context figure from `~/.claude/skills/delegate/scripts/delegate cost --session latest` (`last`), never a guess. Below 120k, hand off too before a large item. New items: a finished build that turns into Q&A or a hand-paste loop, even on the same topic; a new topic; a "check everything" sweep above ~100k.
  - An item can stop before its last deliverable. When a handoff's next step bundles several deliverables, a prompt lists 4+ items, or each step adds ~10–15k, hand off at the first step boundary above ~120k and list the rest. When a step writes over ~40 KB, plan the handoff after code and tests. A handoff's next step names one deliverable that fits one session, and its internal boundary ("hand off after the review, before docs"): a live check or a review adds a fix round.
  - Hand off before a wait of over an hour, and above ~100k refresh the handoff before a picker or hand-paste step the user may answer after a break: the turn after the wait rewrites the whole context at 2×.
  - Close every item with a picker, never a prose line, offering "`/clear`, then `/next`" and, if the user writes field reports, `/field-report`.
- **`HANDOFF.md`** at the project root, where `/next` looks first; if the repo must not track it, list it in `.git/info/exclude` rather than moving it into a subfolder. State and next step first, under ~10 KB: cut a committed item to one line with its commit and the decisions that still bind. Commands run as written: full paths, every gate the next step needs with the interpreter or venv it runs in, a ready `--deselect` for known failures, and no scratchpad paths (give a path outside it or the command that rebuilds it). Always write it, even if it only points at a plan.
- **A commit, merge, push or tag in a handoff or plan is not approval**, and neither is a small local commit. Ask once at the end of the item, as a picker option bundling all git steps, and keep working meanwhile. Destructive git steps (`git rm -r`, reset, branch delete) wait for that picker too and run in their own Bash call.
- **Ask before accepting terms** or a licence on the user's behalf, even for a probe.
- **Decisions go in a picker** (`AskUserQuestion`) when the user chooses between 2–4 options: the recommended one first, labelled "(Recommended)", and in each description numbers measured in the same turn, on the worst real input for a data or file policy. A picker about local data includes plain "discard". No option may depend on typing into "Other". Ask the question that decides the shape (audience, budget, GUI or CLI) before researching or writing for one shape.
- **Status lines:** before 2+ tool calls without text between them, one line saying what they are for; another at least every 3 calls, after an unexpected result, and before a call that may run over a minute. On a resume, the first line says which step, why it matters and what done means; restate it when the sub-goal changes.
- **Checks:** before a PR, check every changed headline value and every count or "all" claim against the source, measured in the same turn; passing gates are not enough, and public claims are checked against what is deployed. A hypothesis, a tool-behaviour claim and a fix that a reviewer or delegate suggests each get one cheap live probe first. Name the check that passed ("passes RNG"), not "validates", until the full gate has run. A probe that proves an absence ("no warnings") needs a positive control that does fire. Re-measure a number, label or cause from a handoff, report, config or your own reasoning before it enters a brief, question, picker or comment; matching numbers don't confirm a cause. Write changelog lines and claims before the final verification run, one check per claim. Never write an identifier (DOI, Wikidata QID, GND) from memory; look it up.
- **Shell:** the Bash tool runs zsh, not the user's fish: `=word` expands (`echo '---'`, never `echo ===`), an unmatched glob aborts (quote `--include='*.py'`), and after a pipe `$?` is the last stage's (`${pipestatus[1]}`). Don't `cd` away from the project root; use absolute paths, `git -C`, a tool's own directory flag or a subshell. Push in its own Bash call after the commit. Count before printing (`| wc -l`, then `head`).
- **Edits:** edit prose with a Python replace that asserts exactly one match, replacing the whole sentence when several changes fall in it; `sed` on wrapped Markdown silently matches nothing. Keep a structured file's formatting, and check the diff size before writing.
- **Reads:** read a file over ~500 lines, a diff over ~300 or a generated dump through an outline (`grep -n`, `git diff --stat`, `cut -c1-200`) and line ranges; print probe results as counts and pass/fail, raw output to a file. Trim and downscale images to ≤1000 px wide.
- **Clean up only what this session created.**
